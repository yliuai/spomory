# 方法论初稿：HippoRAG式检索 + LightRAG式增量图 + GRPO记忆管理（Epic 4.4）

> 面向后续投稿/技术博客的初稿。目的是说明这套组合的设计动机，以及目前
> 实测能支撑、还不能支撑的结论——按 Epic 4 的要求，如实区分两者。

## 1. 问题设定

个人记忆场景的数据特征和典型 RAG 场景不同：**持续、少量增长**，而不是
一次性大批量语料索引。这意味着索引方案的选型标准也不同——不是"检索质量
最高"，而是"检索质量足够高 + 每次新增数据的索引成本可控"。这是本方案
放弃 GraphRAG（索引成本高、每次更新重建整图）、转向 LightRAG 式增量图的
直接动机。

## 2. 系统设计

### 2.1 存储层：双层增量图

`graph/models.py` 定义 `Entity`/`Relation` 独立建模（实体层、关系层），
`graph/incremental.py` 的 `IncrementalIngestor` 每次只处理新增文本：
抽取候选三元组 → 按精确名称/别名匹配做实体消歧（歧义时保守地新建实体，
避免误合并两个同名不同义的实体）→ 只写入新增/更新的节点和边，不重建整图。

### 2.2 检索层：query→triple 匹配 + 个性化 PageRank

参照 HippoRAG 2 的思路，`retrieval/query_match.py` 把查询直接和三元组的
自然语言渲染做 embedding 相似度匹配（而不是只匹配到实体节点），再以匹配到
的三元组端点为种子，用 `retrieval/ppr.py`（`networkx.pagerank` 的
personalization 参数）做一次性扩散，取代逐跳迭代式 RAG。

### 2.3 记忆管理层：GRPO 训练一个决定"记/忘/更新"的策略

`memory_manager/actions.py` 定义 ADD/UPDATE/DELETE/NOOP 动作空间，
`memory_manager/reward.py` 用单一的下游 QA 正确性作为结果导向奖励（对比
Mem-α 的四项奖励，更适合资源有限的团队起步），`memory_manager/train_grpo.py`
用 TRL 的 GRPOTrainer + PEFT LoRA 训练。

## 3. 实测结果：目前能支撑的结论

| 验证项 | 结果 | 验证方式 |
|---|---|---|
| 三元组抽取管道能跑通真实 LLM 调用 | 一段测试文本抽出 3/3 条合理三元组 | 真实 DeepSeek API 调用 |
| Embedding 层能区分中英文语义相近/无关句子 | 语义相近句子余弦相似度明显更高 | 真实本地多语言 embedding 模型 |
| query→triple 匹配能召回需要跨实体关联的正确路径 | 复现了 HippoRAG 2 "不只匹配到节点"的设计意图 | 真实 embedding，人工构造的多跳测试用例 |
| PPR 扩散能召回 3 跳外的关联节点，且排在无关节点之前 | 20+ 节点的人工测试图上验证通过 | 单元测试（确定性图结构，非依赖模型） |
| 增量写入不随图规模线性退化到不可接受程度 | 2000+ 节点图上单次增量写入 < 2 秒 | 单元测试 benchmark |
| 端到端 pipeline（抽取+检索+生成）能正确回答需要关联推理的问题 | 10 个人工构造多跳问题，真实 LLM+embedding 全链路跑通，≥7/10 正确 | 真实 LLM 调用（`tests/test_e2e_real_llm.py`） |
| GRPO 训练脚本的工程链路（数据→LoRA→训练循环）本身能跑通 | 对一个占位小模型完成训练循环，奖励/loss 有真实输出 | 真实 TRL/PEFT 训练循环（占位模型，非生产级） |

## 4. 实测结果：目前还不能支撑的结论（如实说明，不回避）

- **"HippoRAG式PPR比纯向量检索更好"这个结论目前样本量不够**：在 LoCoMo
  数据集一个 6 条问答对的极小子集上，PPR 版本 recall@10 是 83%，纯向量
  基线是 67%（详见 `docs/benchmark_smoke_test.md`），方向上和 HippoRAG
  论文的主张一致，但 n=6 远不足以得出统计显著结论。
- **GRPO 训练对记忆管理策略的实际提升尚未验证**：`train_grpo.py` 的训练
  循环本身跑通了，但用的是占位小模型和玩具数据，不是真实 7-8B 模型 +
  Epic 3.1 要求的 150 条真实标注数据。规则式基线（`RuleBasedPolicy`）已经
  实现并测试，但和真正训练出的策略的对比评估（Epic 3.6）还做不了，因为
  没有真实训练出的 checkpoint 可比。
- **抽取管道对时间信息的处理是一个已发现的真实缺口**：小样本测试里，
  时间类问题（"什么时候……"）系统性答不出来，根本原因是三元组抽取没有把
  对话/文档发生的时间系统性地带入三元组或 provenance——这是下一步要修的
  具体问题，不是笼统的"效果不够好"。

## 5. 局限与下一步

本文档基于开发环境（网络延迟较高、无 GPU 集群、无云端部署）能验证的范围
如实记录。要把第 4 节列的开放问题变成第 3 节的验证结论，下一步具体需要：

1. 更低延迟的网络环境或批量调用优化，跑完 Epic 4.1/4.2 要求的
   100+ 样本正式基准（当前 20 轮对话 + 6 条问答就需要 ~3-5 分钟）。
2. 把时间戳信息带入抽取管道（`graph/extract.py`/`graph/incremental.py`），
   重新跑一遍基准，验证是否能修复时间类问题的系统性失败。
3. 真实 GPU 预算跑 Epic 3.4 的 GRPO 训练（7-8B 模型、150 条真实标注数据），
   才能做 Epic 3.6 的规则式 vs 训练后版本对比。
4. 把 Epic 8.1 的骨架补上公开的 Add/Search 端点，具备提交
   Agent Memory Leaderboard（Epic 4.5，第二轮预计 2026-09-20 开放）的前提条件。
