# Epic 3.6：规则式 vs GRPO 训练后策略对比评估

第一次训练+对比给出的是一个误导性的"没学到东西"结论——往下看会看到，
那个结论本身是两个真实 bug 的产物，不是训练方法或数据规模的问题。修完
之后，训练后的策略在 3 个测试场景上和规则式基线打平（3/3），比修复前
的版本（2/3）更好。记录完整过程，而不是只保留最后的好看数字。

## 第一轮：看起来"没学到东西"，但诊断是错的

用真实 GPU（2×TITAN RTX 24GB）+ 真实 `Qwen/Qwen2.5-7B-Instruct` + 真实
16 条标注样本跑完 3 epoch，训练日志里 `loss`/`grad_norm` 全程为 0。当时
的结论是"16 条样本太少，GRPO 组内奖励方差不够"——**这个诊断后来被证明是
错的**。真正的原因是 `train_grpo.py::_reward_fn` 有一个实现 bug：它没有
根据模型每次采样生成的 completion 内容打分，而是直接把数据集里预先算好
的 `qa_correct` 标签原样返回给同一个 prompt 采样出的全部 4 个 completion
——也就是说，无论模型这次生成了什么，同一组内的 4 个奖励值永远相等，
GRPO 的组内相对优势（以及梯度）因此恒为 0，**跟训练样本数量无关**，
27 条、150 条、1500 条都会是同样的结果。

同时还发现了第二个问题：`memory_manager/policy.py` 的 `TrainedPolicy`
在推理时问模型的问题（"请从 ADD/UPDATE/DELETE/NOOP 中选择一个动作"）
和训练时实际问的问题（"是否应该采纳这个记忆操作？"）完全不是同一个
——模型被拿去回答一个它从没被训练过的问题，决策质量当然无法反映训练
效果。

## 修复

1. **`_reward_fn` 改成真正给每个 completion 单独打分**：解析模型这次
   生成的文本里是"采纳"还是"不采纳"，和 `qa_correct` 标签比对——标签为
   真（这个事实确实帮到了下游问答）就应该"采纳"，标签为假就应该"不采纳"，
   两者一致才给奖励 1。`tests/test_train_grpo.py::test_reward_fn_varies_per_completion_not_just_per_prompt`
   把这个性质锁进了单元测试，防止同类 bug 再犯。
2. **`TrainedPolicy._render_prompt` 改成和训练时完全一致的问法**，推理时
   只问"是否应该采纳"这一个二元问题（模型训练时唯一学过的问题），采纳与否
   之后，具体是 ADD 还是 UPDATE 这个结构性判断复用 `RuleBasedPolicy` 的
   逻辑——模型自己的贡献只是"要不要采纳"这个开关，目前的训练方式还没有
   教会它自主选择 DELETE。
3. 顺手修了 `TrainedPolicy` 推理时没有用 GPU 的问题（`AutoPeftModelForCausalLM.from_pretrained`
   不传 `device_map` 默认整个模型跑在 CPU 上，7B 模型 CPU 推理一次要几十
   分钟；改成和 `train_grpo.py` 一样的 `device_map="auto"`）。

修复后用同一批 27 条样本（16 条 + 又跑了一批 conv-41 独立样本得到的 11
条合并）重新训练，日志里出现了真实的非零 `grad_norm`（0.64、0.52）和非零
`reward_std`（0.05-0.16），`frac_reward_zero_std` 也从恒为 1 降到部分步骤
0.7-0.9——**说明真实梯度信号确实出现了**。

## 决策对比：3 个场景，规则式 vs 两个版本的训练后策略

| 场景 | 期望动作 | `RuleBasedPolicy` | 训练后 v1（16条，奖励函数有bug） | 训练后 v3（27条，奖励函数已修复） |
|---|---|---|---|---|
| 全新事实 | ADD | ADD ✅ | NOOP ❌ | ADD ✅ |
| 完全重复的事实 | NOOP | NOOP ✅ | NOOP ✅ | NOOP ✅ |
| 冲突事实（换工作） | UPDATE | UPDATE ✅ | UPDATE ✅ | UPDATE ✅ |

修复奖励函数和推理prompt之后的 v3 checkpoint，在这 3 个场景上和规则式
基线**打平（3/3）**，比修复前的 v1（2/3）更好。

## 这个结果能说明什么，不能说明什么

**能说明**：训练链路（数据生成→奖励函数→GRPO训练→推理封装）现在是一个
真实、自洽、可工作的闭环，不是摆设；用真实数据训练出的 checkpoint 在
基本场景上至少不比手写规则差。

**不能说明**：
- 这只是 3 个手工构造的简单场景，不是严格的验证集准确率对比。
- 27 条样本全部用于训练，没有切验证集——"和规则式打平"衡量的是训练集
  内的一致性，不是泛化能力。
- 只人工抽查了 3 条，没有达到 Epic 3.5 验收标准建议的 20 条规模。
- 这几个场景规则式基线本来就能做对，训练后策略的价值还没有在规则式
  基线做不到的情况（比如需要结合更复杂上下文判断是否要 DELETE 过时信息）
  上得到验证。

## 下一步

要把这个结果坐实，需要：（1）把数据集按 TASKS.md 建议扩到 ~150 条并切出
真正的验证集；（2）在验证集上跑一次完整的下游 QA 准确率对比（不是决策
一致性对比），这是 Epic 3.6 原本设想的对比形式；（3）扩大人工抽查到 20
条，覆盖规则式基线处理不好的场景（比如需要 DELETE 的情况），才能看出
训练后策略相对规则式基线的真实增量价值在哪里。
