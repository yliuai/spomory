# MVP 最小功能范围（Epic 9.1）

对应创业方案「五、目标用户与冷启动打法」：不直接对齐泛大众个人记忆用户画像，
先收窄到一个具体的专业知识工作者垂直。

## 目标用户

技术顾问 / 软件工程师 / 独立开发者——本身就需要管理大量项目、客户、技术知识，
对新工具接受度高，决策链条短。第一批种子用户优先来自创始人自己的软件工程
背景能天然触达的社群。

## 核心使用场景

把项目笔记、客户沟通记录、技术文档持续喂进个人知识图谱，之后能被检索、
被 Claude Code / Cursor 里的 Agent 调用——不是做一个独立的记忆类 App，而是
让这些工具在对话里"记得住"用户过去的项目上下文。

## 做什么

1. **MCP Server**（Epic 6）：`add_memory` / `search_memory` / `get_graph` /
   `export_memory` 四个工具，接入 Claude Desktop / Cursor。
2. **批量导入**（Epic 9.2，已实现见 `memory_core/onboarding.py`）：
   一次性把已有的 Markdown/纯文本笔记文件夹导入图谱。
3. **本地优先**：默认 `LocalGraphStore`（SQLite），不强制注册云端账号
   才能用起来。
4. **记忆护照导出/真删除**（Epic 7，已实现）：作为免费层能力，不是
   营销噱头。

## 明确不做（本阶段）

- **不做泛大众 C 端界面**——没有独立的聊天类 App/网页产品，只做开发者工具
  和它接入的客户端（Claude Desktop/Cursor）。
- **不做 PDF/语音/图片导入**——Epic 9.2 只支持 Markdown/纯文本；PDF 后置，
  语音/图片属于 Epic 5（多模态），本阶段不投入。
- **不做浏览器插件**——跨平台覆盖 ChatGPT/Gemini 等消费级网页端的插件是
  Phase 2 的事（对应方案第四部分），MVP 阶段只做 MCP 能覆盖的开发者客户端。
- **不做团队版/多用户协作**——单用户个人记忆图谱，权限模型、共享/协作
  留到验证完个人版留存后再看（对应方案 Phase 3 的分岔决策）。
- **不做完整计费系统**——Epic 8.1/8.3 只搭了认证+配额骨架，真正上线收费
  需要先有付费意愿信号再投入完整 Stripe 集成。

## 验收信号（呼应方案 Phase 1 成功指标）

首批种子用户次月留存、首批付费转化率、NPS/定性访谈信号——而不是功能数量。
