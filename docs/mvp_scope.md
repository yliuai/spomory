# MVP 最小功能范围（Epic 9.1）

对应创业方案「五、目标用户与冷启动打法」：不直接对齐泛大众个人记忆用户画像，
先收窄到一个具体的专业知识工作者垂直。

## 目标用户

技术顾问 / 软件工程师 / 独立开发者——本身就需要管理大量项目、客户、技术知识，
对新工具接受度高，决策链条短。第一批种子用户优先来自创始人自己的软件工程
背景能天然触达的社群。

## 核心使用场景

把项目笔记、客户沟通记录、技术文档持续喂进个人知识图谱，之后能被检索、
被 Claude Code / Cursor 里的 Agent 调用——不是做一个独立的记忆类 App，而是
让这些工具在对话里"记得住"用户过去的项目上下文。

## 做什么

1. **MCP Server**（Epic 6）：`add_memory` / `search_memory` / `get_graph` /
   `export_memory` 四个工具，接入 Claude Desktop / Cursor。
2. **批量导入**（Epic 9.2，已实现见 `memory_core/onboarding.py`）：
   一次性把已有的 Markdown/纯文本笔记文件夹导入图谱。
3. **本地优先**：默认 `LocalGraphStore`（SQLite），不强制注册云端账号
   才能用起来。
4. **记忆护照导出/真删除**（Epic 7，已实现）：作为免费层能力，不是
   营销噱头。

## 明确不做（本阶段）

- **不做泛大众 C 端界面**——没有独立的聊天类 App/网页产品，只做开发者工具
  和它接入的客户端（Claude Desktop/Cursor）。
- **不做 PDF/语音/图片导入**——Epic 9.2 只支持 Markdown/纯文本；PDF 后置，
  语音/图片属于 Epic 5（多模态），本阶段不投入。
- **不做浏览器插件**——跨平台覆盖 ChatGPT/Gemini 等消费级网页端的插件是
  Phase 2 的事（对应方案第四部分），MVP 阶段只做 MCP 能覆盖的开发者客户端。
- **不做团队版/多用户协作**——单用户个人记忆图谱，权限模型、共享/协作
  留到验证完个人版留存后再看（对应方案 Phase 3 的分岔决策）。
- **不做完整计费系统**——Epic 8.1/8.3 只搭了认证+配额骨架，真正上线收费
  需要先有付费意愿信号再投入完整 Stripe 集成。

## 验收信号（呼应方案 Phase 1 成功指标）

首批种子用户次月留存、首批付费转化率、NPS/定性访谈信号——而不是功能数量。

## Epic 11.6：ICP 再确认（2026-09，基于竞品分析）

Epic 9.1 定的"技术顾问/工程师"垂直是 MVP 阶段的收窄，Epic 11.6 是基于
MemoryPlugin/Mnemoverse/Mem0 等七款竞品的分析（见"Spomory 竞品分析"内部
战略文档），在三个候选方向里重新做一次选择：

1. 开发者/技术爱好者的本地优先记忆引擎
2. 消费级跨 App 记忆
3. 企业记忆治理

**决定：同时投入方向 1 + 方向 2，方向 3 暂不投入，等前两者跑出验证信号
（留存、付费转化）后再评估要不要做。**

### 为什么是这两个一起做，而不是三选一

方向 1（开发者本地优先）不是全新方向，是 Epic 9.1 结论的延续和确认——
第一批种子用户、`docs/mcp_quickstart.md` 里的本地 stdio 接入路径、
"记忆护照"真删除这些已经做的事，价值主张没变。

方向 2（消费级跨 App 记忆）是这次真正新增的范围：现有本地版只能被
Claude Desktop/Cursor 这类能在本机拉起子进程的客户端使用，覆盖不到手机
App、网页版 ChatGPT/Gemini 这类没法装本地环境的场景——而这批用户
恰好是"记忆需要跨多个 App 用"这个诉求最直接的受众。这两个方向对应的
其实是同一套核心能力（记忆图谱的抽取/检索/管理）在两种不同分发形态下
的呈现，不是要做两套产品，投入不冲突。

方向 3（企业记忆治理）暂不投入，是因为它需要的东西（多用户协作、权限
模型、SSO、面向合规的审计能力）跟前两个方向几乎不共享——`docs/mvp_scope.md`
"明确不做"里"不做团队版/多用户协作"这条结论继续成立，等方向 1/2 验证出
真实付费意愿后再看是否值得单独投入一条产品线。

### 对 Epic 11.5（远程 MCP 服务）的影响

这次决定把远程服务的定位从"可选的第二种接入方式/上架各家 MCP 广场的
前提条件"，提升成了"方向 2 用户的核心产品形态"——本地 stdio 版能满足
方向 1，但方向 2（消费级跨 App）用户天然需要一个不依赖本机环境、能被
多个 App 同时访问的记忆后端，这正是 `src/memory_core/mcp_server/remote.py`
+ `src/cloud_api/` 已经在建的东西。也呼应了更早讨论过的"本地版是否还有
必要保留"的结论：方向 1 用户继续用本地版（免费、隐私优先、零基础设施
成本的获客入口），方向 2 用户走远程版（账号+云端存储），两条线服务不同
用户群，不是互相替代关系。

### 对定价的影响

`src/cloud_api/billing.py` 现有的 free/weekly/monthly/annual 阶梯定价
（避免 Mem0 19→249 美元 13 倍跳档的问题）是针对个人开发者/消费者设计的，
方向 1、2 都直接适用，不需要现在就为了方向 3 去设计企业合同定价（按
坐席收费、SSO 附加费之类）——这部分推迟到方向 3 真正被激活时再补，
现在硬做只会增加复杂度但没有对应的付费用户验证。
